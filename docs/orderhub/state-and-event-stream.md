# 快照与补流契约

状态：设计评审稿，待实现。返回 [改造方案](../../orderhub-oms-transformation.md)。

## 对外状态的来源

GetState 与 WatchEvents 读取同一份已提交的 OrderHub 业务投影，使用同一版本线。
不能从正在变化的 Nautilus Cache 读取一半字段，再拼接另一版本的业务日志。
核心回报先形成规范化业务事件，持久提交完成后才能进入一致性投影和对外事件流。
订单受理 ACK 同样在该提交完成之后返回。

Nautilus Cache 可暂时领先对外投影，但在此窗口内必须保留保守额度和限制，
不能根据尚未持久化的释放结果批准下一笔新单。

## 四个 RPC 的查询形态

保持四个业务 RPC，通过 GetState 请求的 `oneof` 区分查询形态：

| 查询            | 请求               | 响应                             |
| ------------- | ---------------- | ------------------------------ |
| Snapshot      | 授权视图、可选分页 token。 | 活跃订单、持仓、账户、合约元数据、业务状态、快照标识和游标。 |
| OrderLookup   | 指定订单 ID，数量有上限。   | 活跃或终态订单、归属、累计成交、剩余量、最终状态及版本。   |
| RequestLookup | 原 RPC 方法与请求 ID。  | 原受理/拒绝结果、关联订单及状态；不限于活跃订单。      |

查询始终校验权限。策略只能读取授权数据；账户总资金及其他策略详情是否可见由显式权限决定。
交易端若需要账户全局视图，使用独立授权，不能靠客户端传一个全局过滤条件获得权限。

不存在、详情已归档、请求代已失效、来源不确定需要分别表达。
历史窗口外查询不到订单不是“从未下单”的证明，客户端不得因此自动新建替代请求。

## 标识与版本

| 字段                    | 语义                                      |
| --------------------- | --------------------------------------- |
| `journal_epoch`       | 连续业务日志的代号；正常进程重启保持不变。                   |
| `event_seq`           | 此日志代内已提交业务事件的单调序号，跨正常重启延续。              |
| `event_id`            | 稳定去重身份；重放与重连保持不变。                       |
| `snapshot_id`         | 一个固定版本的状态快照；分页过程中不改变数据集。                |
| `state_cursor`        | 快照覆盖到的业务日志位置 N，不以时间戳代替顺序。               |
| `resume_token`        | 服务端签名的不透明 token，绑定日志代、位置、提交方、授权版本和过滤条件。 |
| `instrument_revision` | 元数据版本，关联精度、tick、交易状态及通道能力。              |

业务序号不直接复用 Nautilus event_store 的 per-run `seq`。
协议中的 64 位序号、纳秒时间戳在 JSON/grpcurl 展示时使用字符串，避免 JavaScript 数值精度损失。
金额、数量使用十进制字符串或明确的整数加 scale，零值和字段缺失分别表达。

## 快照和订阅衔接

1. 在同一个投影版本固定数据集和游标 N，建立限时快照租约。
1. 返回所有快照页；每页绑定相同 `snapshot_id`、授权视图和游标 N。
1. 客户端完成快照安装后，以返回的 token 请求 `WatchEvents(after=N)`。
1. 服务端从持久日志扫描 N 之后的事件，并连续跟进新提交事件，不能在历史扫描与实时订阅之间留下空隙。
1. 客户端原子应用一条事件与其恢复 token，断线后从最后成功应用的位置继续。

实现可使用“先注册唤醒信号，再扫描持久日志并反复追赶”的方式。
内存广播只用于唤醒，持久日志决定扫描范围；不能把一条可能丢失的内存广播作为唯一交付依据。

快照租约固定分页数据，且保护后续补流所需日志直到约定租约期限。
租约有数量、字节和持续时间上限，避免慢客户端阻止无限日志回收。
快照或 token 已过期时显式返回 `OUT_OF_RANGE` / `RESYNC_REQUIRED`，客户端重取快照。

## 事件流内容与过滤

WatchEvents 使用统一 envelope，`oneof` 至少覆盖订单、成交、持仓、账户、合约变更、
业务就绪状态和连接状态。原因码和枚举留有未知值兼容路径，禁止重用已发布字段编号。

策略过滤后的序号允许跳号，因为中间事件可能属于其他策略。
客户端不能据此认定丢事件，也不能通过跳号推断其他策略详情。
服务端可发送 progress 帧，携带已经完整扫描的位置，用于推进没有相关业务事件时的恢复游标。
progress/心跳帧不计作订单业务事件，不伪造业务变更。

连接状态可映射内核发布的 `SocketStateChanged`；适配器发出的原始消息是 `SocketStateChange`。
连接就绪与业务可交易分开表达；`READY` 的具体条件见 [恢复契约](recovery-and-reconciliation.md)。

## 慢消费者与故障行为

- 每个订阅都有有界发送缓冲。客户端慢时暂停扫描；超出资源或保留期限就关闭该流并提供恢复原因。
- 不阻塞核心线程，不无限缓存，不静默丢弃订单或成交事件。
- 服务端可以重复交付事件；客户端按 `event_id` 或已应用游标去重。
- 权限变化使旧视图 token 失效，客户端必须重新获取授权快照。
- 日志写入故障时，不能以尚未落盘的新事件推进游标或对外继续宣称 READY。
  立即关闭相关流或返回不可用；若还能查询，附带独立实时健康字段 `writable=false`、`stale=true`。
- 实时健康字段仅报告服务当前能否安全工作，不推进一致性快照游标；恢复后以持久事件补记状态变化。

## 终态与日志保留

活跃订单快照不承担全部历史查询。终态订单及请求键索引需要独立保留，
即使事件补流窗口结束，仍能查询已受理请求的结果或明确的归档状态。
幂等防重记录不能与短期流事件一同过期删除。

保留周期、快照 TTL、分页大小、订阅数量和磁盘容量属于部署参数，需在 M2 前定值。
回收必须保证最近可恢复检查点及其日志尾仍完整，不能仅按文件年龄删除。

## 验收场景

| 编号  | 场景                | 必须成立                                 |
| --- | ----------------- | ------------------------------------ |
| S01 | 读取快照期间持续下单成交。     | 快照固定在 N，N 之后事件完整，无状态拼接。              |
| S02 | 历史扫描追上实时流的瞬间产生事件。 | 该事件至少交付一次，没有切换空隙。                    |
| S03 | 断线期间订单成交或撤销。      | 补流或 OrderLookup/RequestLookup 能确认终态。 |
| S04 | 分页途中订单状态变化。       | 所有页属于同一 snapshot_id，不重复、不漏记录。        |
| S05 | 慢消费者、缓冲溢出、旧游标。    | 核心持续运行；显式断流或重同步，不静默漏单。               |
| S06 | 正常重启及旧备份恢复分别重连。   | 前者延续日志代，后者拒绝旧代 token。                |
| S07 | 过滤流出现序号跳跃或权限改变。   | 跳跃可解释，旧授权 token 不能继续读取。              |
| S08 | 存储故障但网络连接仍正常。     | 不返回虚假的 READY；不发布未持久事件。               |
