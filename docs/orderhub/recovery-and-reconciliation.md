# 重启与对账契约

状态：设计评审稿，待实现。返回 [改造方案](../../orderhub-oms-transformation.md)。

## 当前上游能力与新增职责

依据核对基线，现有 event_store 捕获是异步的，halt 信号不会自动阻断交易。
它存储 Cache 快照的锚点及哈希，快照 blob 仍需要自己的持久化位置。
显式 `replay_from_run_id` 启动执行状态回放并跳过实盘启动，不能直接视作完整恢复交易流程。

证据见 [Event sourcing](../concepts/event_sourcing.md)、
[Cache::load_snapshot_blob](../../crates/common/src/cache/position.rs)、
[内核启动](../../crates/system/src/kernel.rs) 和
[EventStoreBusTap::capture](../../crates/event_store/src/kernel.rs)。

建议新增 OrderHub 业务日志，以独立 redb 存储空间实现单写者事务，置于 gateway 模块中。
本轮仅提出设计，不复用或修改上游私有 run 文件格式。
本地持久提交只保证在存储设备遵守刷盘语义时的进程/主机崩溃恢复，不等同于磁盘损毁后的零数据丢失。

## 持久化清单

| 数据        | 恢复要求                                                     |
| --------- | -------------------------------------------------------- |
| 幂等索引与请求结果 | 保留请求摘要、订单 ID、日志代及稳定结果，压缩后仍防重。                            |
| 订单意图与派发状态 | 恢复待发单、已进入不确定发送窗口的订单，以及未完成撤单意图。                           |
| 风险账本      | 暂占的恢复决策、正式预占、持仓/现金/费用占用、规则版本和计算依据。                       |
| 身份与归属     | 稳定提交方/策略 ID、账户路由及订单归属；凭证秘密不写进事件日志。                       |
| 合约与映射     | 合约定义版本、Nautilus ID、券商合约 ID、客户/券商订单 ID 和成交 ID。            |
| 引擎恢复材料    | 已验证可重建订单、账户、持仓的快照或完整事件集合；不只保存持仓帧。                        |
| 业务投影与事件   | 已提交高水位、快照版本、对外事件、终态详情及订阅恢复位置。                            |
| 生命周期      | 实例 ID、日志代、schema 版本、二进制 SHA、配置哈希和关联的 event_store run ID。 |

OrderHub 业务事务原子提交自身的请求、额度、状态和事件。
与 Nautilus event_store 的写入不构成原子事务，不能把“两个日志各自存在”当作一致性证明。
重放去重按稳定 ID 进行；相同事件出现两份记录不会应用两次经济变化。

持久化工作线程可以批量提交多个独立请求，只有 durable commit 成功后才确认整个批次。
磁盘提交与主线程通过有界消息往返，任何缓存层都不能先发 ACK 再后台尝试落盘。

## 检查点

检查点必须覆盖同一逻辑版本 N 的完整恢复材料，包括业务账本、身份归属和引擎需要的状态。
发布顺序为：固定版本、持久写入不可变 blob、验证哈希、持久发布清单和 N，再允许回收旧日志。
检查点文件使用唯一标识，不覆盖仍被引用的 blob；中途崩溃留下的未引用 blob 不作为恢复依据。

内核快照与业务检查点不能凭时间戳近似配对。M0 必须选择暂停派发/排空回报形成一致切面，
或实现经过验证的版本屏障；同时记录引擎 event_store 水位与 OrderHub 水位的关联。
不能把任意一张持仓快照当作完整账户和订单检查点。

读取检查点失败时可回退到经过验证的更早检查点加完整日志尾；若历史不足则停机修复，
不能忽略缺失记录后直接开放交易。

## 业务就绪状态

以下状态属于 OrderHub 控制面，不替换 LiveNode 原生生命周期：

```text
BOOTING -> RESTORING -> RECONCILING -> READY
任意状态 -> HALTED
READY -> DRAINING -> STOPPED
```

只有身份配置、持久化、合约/账户数据、所需行情、执行连接和对账全部满足要求，才能进入 READY。
最初采用全节点保守门禁；未来隔离单账户故障时必须显式定义门禁作用域。
恢复失败返回 HALTED 和可诊断原因，不仅记录日志后对外返回正常。

## 启动顺序

1. 获取单活锁，验证数据目录、schema、实例身份、配置和二进制兼容性；未取得独占权不能连接执行通道发单。
1. 恢复业务检查点和日志尾，重建请求索引、归属、额度及订阅投影；保守保留不确定订单占用。
1. 使用已验证路径恢复 Nautilus Cache 与引擎所需状态，关联现有 event_store；禁止把历史命令作为实盘命令重新广播。
1. 加载最新合约，建立行情与执行连接，通过 LiveNode 生命周期完成初始数据加载和回报处理。
1. 获取目标账户的活跃订单、必要终态订单、成交记录和持仓，验证查询窗口及分页覆盖是否完整。
1. 将外部事实与本地请求、订单及策略归属对齐，幂等应用迟到成交和修正，重算保守额度。
1. 对未解决差异保持门禁，记录具体订单/账户和待补证据；不能仅凭账户净数量相同就判定全部恢复。
1. 持久记录恢复结果和 READY 转换后开放 SubmitOrder；待发单在重新验证规则和业务截止时间后才能派发。

恢复期间查询可返回带 `stale` 标记的已知快照。撤单是否可用取决于订单身份是否可信、
通道是否就绪及请求能否持久记录；不会因为“禁止新单”自动禁止所有撤单，也不宣称未知订单已撤销。

## 崩溃窗口与派发决策

| 最后可信记录                        | 恢复动作                             |
| ----------------------------- | -------------------------------- |
| 没有受理事务                        | 同代同键重新提交需先检查恢复完整性；完整性未知时不受理。     |
| 受理已提交，确定没有 `DISPATCH_STARTED` | 证明尚未发出；检查撤单、截止时间和动态风控后可派发。       |
| 已有 `DISPATCH_STARTED`，缺少可信结果  | 视为可能已发送，按稳定订单标识查询，禁止默认重发。        |
| 通道已接单，本地仅缺回报                  | 补齐订单和成交，保持原订单 ID 与归属。            |
| 发单查询返回空，但历史窗口/覆盖不完整           | 保持不确定及占用，不能解释为从未接单。              |
| 已有可信终态及累计成交                   | 幂等结转额度，允许客户端查询历史结果。              |
| 待撤请求尚无最终回报                    | 查询订单真实状态，在通道语义允许时继续撤单；不释放未证实的占用。 |

只有目标通道明确支持同一客户订单 ID 的安全重发，且已验证其作用域、保留期和行为时，
才可为该通道增加受约束重发策略；默认策略是查询对账。
模糊拒绝、连接错误和传输超时不得被归类为“确定未执行”。

## 策略归因与美股恢复

券商账户净持仓不能独立恢复多个策略归属。
本地 A +10、B -8 与券商净 +2 必须保留为两份策略账本和一份账户外部事实。
缺失归属的订单或成交进入显式 `EXTERNAL`/未归因桶并计入账户风险，不随意分配给某策略。

卖空、融资、碎股、拆股等范围未确定前不自动推断其经济含义。
若对账发现公司行为或其他无法解释的数量/价格变化，阻断相关账户新增风险并进入恢复处理，
不能通过伪造成交来消除差异后宣称归因正确。
交易日边界、时区、日终费用及晚到成交需要在目标适配器测试中验证。

## 存储故障、单活与备份

- 监听业务日志故障及上游 event_store halt。发现后立即关闭新增风险准入，并阻止尚未发送的新单。
- 已经到达通道的订单无法回滚；回报继续尽力接收，缺失部分必须由恢复对账处理。
- 业务日志不可写时，常规 RPC 不返回持久受理成功。紧急撤单可由独立券商终端执行，后续纳入外部对账。
- 本地文件锁只防止同一主机/共享锁域重复启动；复制数据目录到另一主机不能自动形成安全故障切换。
- 首期只允许一个活动交易节点。跨主机接管需先隔离旧进程及其通道连接，未完成隔离不允许新节点发单。
- 备份必须是一致性备份，包含检查点、完整日志尾、映射和恢复清单；不拷贝写入中的数据库文件冒充一致备份。
- 恢复旧备份导致日志连续性无法证明时分配新 `journal_epoch`，使旧变更请求和订阅 token 失效，
  对账完成前保持 HALTED；换代不能恢复已经丢失的策略归属。

生产前确定备份 RPO、恢复 RTO、磁盘满阈值、日志保留和监控责任。
正常进程重启在本地日志完整时应找回全部已确认受理记录；介质损毁的可恢复范围受备份 RPO 限制。

## 验收场景

| 编号  | 故障注入                       | 必须成立                         |
| --- | -------------------------- | ---------------------------- |
| C01 | 受理提交、回复、派发边界分别杀进程。         | 每笔请求落在明确恢复分支，没有无证据重发。        |
| C02 | 磁盘满、写入报错、event_store halt。 | 新单门禁关闭，不再返回虚假的持久受理成功。        |
| C03 | 写快照、发布清单、回收日志之间崩溃。         | 至少保留一组完整恢复材料，不引用半写快照。        |
| C04 | 重复启动、复制目录到另一主机。            | 同机独占有效；跨机接管要求旧节点已被隔离。        |
| C05 | 断线期间成交、重连重复回报、查询窗口缺失。      | 幂等结转；覆盖不足保持不确定。              |
| C06 | 同账户多策略净额相抵、外部人工交易。         | 账户总量与策略归属分别核对，未知归属不被猜测。      |
| C07 | 备份回退、schema 不兼容或检查点哈希失败。   | 不直接进入 READY；旧代请求无法作为新单重放。    |
| C08 | 超时新单积压后恢复连接。               | 超过 submit_before 的未发送新单不再发出。 |
