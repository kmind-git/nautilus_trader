## 已知需求与待明确口径

用户提出股票资产、以美股为例，以及每秒 1000 笔提交、1000 笔撤单。
这意味着两个方向同时运行时共 2000 个变更请求/s，不包含行情、回报、查询和事件扇出。
目前按系统接入峰值准备设计与压测计划；是否要求实盘持续发出同等速率尚待确认，
此暂定口径不等于降低原需求，也不代表目标已经测得。

最终应分别记录接入峰值、峰值持续时间、持续平均速率、真实通道发出速率和端到端延迟。
如果要求实盘持续发出 1000 + 1000，请先完成通道配额与接入资格选型，不能用内部排队掩盖吞吐不足。

## IBKR 速率限制的含义

2026-09-20 查阅的 [IBKR 官方 pacing 说明](https://www.interactivebrokers.com/docs/tws-api/doc/pacing-limitations/introduction)
将 TWS 请求额度与最大行情行数关联，默认 100 行对应每秒 50 次请求，并提示高频请求可能排队。
该页另列出经 IB Gateway 的 FIX 为每秒 250 条消息；独立 FIX 不使用相同的固定上限。
这些是接口说明，不构成当前账户的吞吐保证，独立 FIX 仍须确认实际接入与容量。

因此建议将现成 IBKR 适配器定位为首个功能验证候选。
若业务要求持续向真实通道发出 2000 请求/s，则需要独立完成机构执行通道选型与新增适配器评估。
不得通过增加 TWS client ID 或连接数量来假定可以线性扩大账户级容量。

## 接入和发送容量必须分开

定义请求流量时避免“全被拒绝但处理很快”被计为成功吞吐：

| 指标                  | 起止位置或定义                                  |
| ------------------- | ---------------------------------------- |
| `offered_rps`       | 压测客户端实际产生的请求数，分提交、撤单统计。                  |
| `admitted_rps`      | 业务日志 durable commit 成功、产生稳定受理结果的请求数。     |
| `rejected_rps`      | 按鉴权、格式、风控、容量、截止时间、通道原因拆分，不计成功受理。         |
| `dispatch_rps`      | 已进入执行通道发送边界的请求数，不能等同于远端确认数。              |
| `venue_ack_rps`     | 通道确认接受/撤销等结果数，提交与撤单分别统计。                 |
| `admission_latency` | 请求到达 gateway 至持久受理结果，报告 P50/P95/P99/max。 |
| `dispatch_wait`     | 持久受理至开始派发的等待时间。                          |
| `venue_latency`     | 开始派发至匹配的通道回报；单独报告网络与通道因素。                |
| `event_lag`         | 业务变化持久提交至订阅者收到/应用的延迟。                    |

在模拟通道容量充足、行情/账户有效、额度充足的有效流量测试中，
目标是同时受理 1000 提交/s 和 1000 撤单/s，不以容量拒绝抵充通过数量。
必须把日志、额度、回报处理和事件扇出全部打开，不能只测空 gRPC handler。

在低容量真实通道前，设计目标是正确处理 2000 请求/s 的入口流量，但多数可能被明确限流拒绝；
这只能证明过载控制，不能报告为完成了相同速率的真实交易。

## 排队预算

设通道总许可为 C 消息/s，撤单预留为 Rc，查询/恢复预留为 Rq，则新单稳态预算最多为：

```text
新单预算 <= C - Rc - Rq
输入持续高于 C 时，积压增速 = 输入速率 - 实际处理速率
```

该表达仅作容量规划；实际消息权重、突发窗口、账户/连接共享关系按通道规则配置。
1000 提交/s + 1000 撤单/s 面对远低于该速率的通道时，有界队列只能吸收短暂突发，
不能解决持续超载。新单超出容量立即拒绝或在有明确截止时间的短队列内等待。
撤单有独立队列和预留调度份额，但同样受共享配额约束。

## 建议的压测计划

以下规模和时长是可复现测试建议，P99 延迟门槛、真实业务规模和机器规格尚待定。
先记录 CPU、内存、磁盘、操作系统、Rust 构建 profile、配置与提交 SHA，再比较结果。

| 场景        | 建议输入                               | 主要验收                                 |
| --------- | ---------------------------------- | ------------------------------------ |
| L01：功能基准  | 本地确定性行情、少量下单/撤单/成交。                | 所有状态和账本一致，建立正确性基线。                   |
| L02：有效流量  | 同时 1000 提交/s + 1000 撤单/s，持续 10 分钟。 | 模拟通道充足时达到受理目标，无丢单/重复执行/额度漂移，队列无持续增长。 |
| L03：热点竞争  | 多提交方竞争同账户、同合约。                     | 原子预占、公平性、账户总限额；单独统计预期风控拒绝。           |
| L04：突发过载  | 目标负载的 2 倍持续 10 秒后恢复。               | 有界内存、明确拒绝、撤单预留有效，负载回落后能排空。           |
| L05：慢通道   | 模拟通道显著低于入口速率。                      | 发送严格限流，不无限排队，不迟发过期新单。                |
| L06：消费者压力 | 多正常订阅者加一个暂停读取的订阅者。                 | 慢消费者不阻塞交易，断线可补流，扇出成本可量化。             |
| L07：故障负载  | 在 L02 期间杀进程、断网、注入写盘错误。             | 持久受理可恢复，未知发单不重复，门禁正确。                |

L02 可先以 10 个提交方、100 个合约、约 10000 个活跃订单作为明确标注的测试夹具，
之后按实际目标扩大；不能将夹具规模当作已确认业务上限。
撤单必须针对已经受理并处于可撤状态的订单，不能用随机不存在 ID 的快速拒绝冒充撤单吞吐。
压测器按固定计划产生开放式负载，记录无法按计划发出的积压，避免等待前一响应造成负载自动降低。

日志容量根据实际事件放大率计算，而不是简单按 2000 条/s 估算。
应测量每次变更产生的事务、事件、索引、快照和字节数，结合交易时长、保留期及备份估算磁盘需求。

## 美股特有的实施前选择

- `DAY` 是否加入首期：原计划只有 GTC/IOC/FOK；在选定通道后明确需求及支持情况。
- 是否只支持整股 USD 多头及卖出现有持仓；融资、卖空、碎股、ETF 和盘前盘后逐项决定。
- 交易日历和美东时区如何获得；不以固定 UTC 时刻替代夏令时与交易日历。
- 合约身份至少含券商合约 ID、币种、主上市地和路由信息，不能只靠股票代码匹配。
- 价格步进、交易暂停、公司行为、成交撤销/修正和费用回报的处理必须覆盖目标通道。
- 可用订单组合以能力表公开；不将客户端传入的 post_only/reduce_only 静默丢弃。

完成这些选择后再冻结实盘能力表。当前没有运行通道压测，也没有连接任何真实交易账户。
