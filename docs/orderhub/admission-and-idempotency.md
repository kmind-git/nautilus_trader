# 受理与幂等契约

状态：设计评审稿，待实现。返回 [改造方案](../../orderhub-oms-transformation.md)。
本文的请求状态属于 OrderHub 协议，不修改 Nautilus 原生订单状态枚举。

## 保证与边界

- 同一请求键的重试返回同一受理结果，不重复建立订单、预占额度或生成发单意图。
- `ADMITTED` 表示请求与预占已持久化，后续执行仍可能被原生风控或执行通道拒绝。
- `ADMITTED` 不代表交易所已接单；交易所接受和成交分别通过订单事件表达。
- RPC 超时、断连、`UNAVAILABLE` 不能证明请求未执行。客户端保留原请求键重试或查询。
- 不承诺跨网络恰好一次执行；不确定发单通过对账解决，不自动换订单 ID 重发。

gRPC 允许状态变更已经成功时返回 `DEADLINE_EXCEEDED`，见
[官方状态码说明](https://grpc.io/docs/guides/status-codes/)。

## 身份与请求键

拟议键为 `(journal_epoch, submitter_id, rpc_method, request_id)`。
`submitter_id` 来自服务端凭证映射，`strategy_id` 必须属于该凭证的授权集合。
常规重启不改变 `journal_epoch`；日志连续性被破坏时的换代规则见 [恢复契约](recovery-and-reconciliation.md)。

| 字段                    | 约定                                       |
| --------------------- | ---------------------------------------- |
| `request_id`          | 客户端生成的唯一请求 ID；同一业务意图重试时保持不变。             |
| `journal_epoch`       | 从 GetState 获得；用于拒绝恢复旧备份后带旧代号的变更请求。       |
| `strategy_id`         | 客户端选择的授权策略，服务端校验，不作为身份凭据。                |
| `client_order_id`     | 服务端在首次受理时分配并持久化；重试返回原值，重启不能重用。           |
| `request_fingerprint` | 规范化业务字段的摘要；不包含 token、传输 deadline 等瞬态字段。  |
| `submit_before`       | 本次订单允许首次向通道发出的业务截止时间；与 gRPC deadline 分开。 |
| `risk_config_version` | 实际准入使用的风控版本；客户端不能指定更宽松的历史版本。             |

摘要覆盖策略、路由、账户、合约、方向、数量、价格、订单类型、有效期、交易时段选项、
`post_only`、`reduce_only` 和 `submit_before`。金额及数量用十进制定点表达，禁止 float/double。
相同键且摘要不同返回 `ALREADY_EXISTS` 和 `IDEMPOTENCY_CONFLICT`，不得覆盖旧记录。
幂等占位记录保留整个日志代的生命周期；事件流压缩或终态详情归档不允许删除防重索引后复用键。
订单 ID 的唯一命名空间必须覆盖日志代，防止恢复旧备份后计数器回退导致 ID 重用。
映射到券商整数 ID 或受长度限制的客户 ID 时，需要持久化映射并验证无碰撞，不能简单截断字符串。

## 首次提交的顺序

1. tonic 校验身份、字段大小、协议版本、授权范围，并取得有界接入许可。
1. 核心线程查询幂等索引；已有完成记录直接返回，处理中记录合并等待者，避免重复进入风控。
1. 检查业务就绪、截止时间、合约规则、通道能力和额度；在内存中登记暂占额度。
1. 将请求结果、订单意图、额度预占及待发送记录作为同一业务事务提交给持久化工作线程。
1. 工作线程确认持久提交后，核心线程将暂占转为正式预占，发布已提交状态并返回 `ADMITTED`。
1. 调度器取得通道发送许可，再检查截止时间和动态准入条件；过期或不再允许发送则持久拒绝并释放预占。
1. 持久记录 `DISPATCH_STARTED`，收到提交确认后才初始化 Nautilus 订单并进入原生 RiskEngine 执行链路。
1. 接收引擎或通道回报，将规范化结果、额度变化和对外事件持久提交，再使查询投影和订阅可见。

初次业务拒绝使用 `REJECTED` 结果及稳定原因码，持久记录后重试仍返回原拒绝。
在能够登记请求前出现的鉴权、格式、容量错误使用 gRPC 状态码，不假装生成了订单。
日志提交结果不确定时，进入故障状态并查询/恢复事务，不能先释放暂占再接受新订单。
客户端断开只取消等待回复；已经受理的请求不会因 RPC 被取消而自动撤单。

`DISPATCH_STARTED` 是保守的不确定边界。崩溃可能发生在此记录提交后、实际发送前，
也可能发生在远端接受后、回报持久化前；两种情况都不能仅凭本地缺少回报判断未发送。
恢复规则见 [重启与对账](recovery-and-reconciliation.md)。

## 订单与请求结果

| 场景         | 响应与后续动作                                   |
| ---------- | ----------------------------------------- |
| 首次持久受理     | 返回请求键、`ADMITTED`、订单 ID、受理版本；订单当前状态可仍为待发送。 |
| 同键同参数重试    | 返回原受理/拒绝结果；另附当前状态版本，或用 GetState 查询。       |
| 同键仍在提交事务   | 合并等待，受 deadline 限制；不创建第二个事务。              |
| 同键不同参数     | 返回幂等冲突，不建立新订单。                            |
| 超时但提交结果未知  | 客户端查询原请求键或同键重试；禁止将其当作拒单并另造请求键。            |
| 已完成订单详情被归档 | 返回已使用请求键和订单 ID；详情不可用要显式说明，不能当成新请求。        |

## 撤单与撤单重下

`CancelOrder` 使用独立请求键，明确指定 `client_order_id`，并校验订单归属及撤单权限。
撤单受理只代表撤单意图已持久化；订单最终可以是撤销、成交或撤单被拒绝。

- 尚未记录 `DISPATCH_STARTED` 的订单：在同一业务事务内取消待发送记录并释放额度，产生本地撤销事件。
- 已进入发送边界的订单：保留额度，发出撤单或等待通道所需的订单标识；查明状态前不得宣称已撤销。
- 同键重复撤单：返回原撤单请求结果；不同键指向同一待撤订单可合并通道操作，分别记录请求关联。
- 已有可信终态：返回 `ALREADY_TERMINAL` 及真实终态；已成交不能包装成撤单成功。
- 撤单期间成交：先应用成交及持仓变化，撤单确认后仅释放剩余未成交部分。

撤单重下由提交方使用两个请求完成。必须等到原单终态明确后，根据已成交数量计算新单剩余量。
原单未知时不自动发替代订单，也不重用原单 ID。

## 验收场景

| 编号  | 输入/故障                       | 必须成立                           |
| --- | --------------------------- | ------------------------------ |
| A01 | 100 个并发请求使用同键同参数。           | 一个订单 ID、一笔预占、一个首次发单意图。         |
| A02 | 同键更改数量、策略、路由或价格。            | 拒绝冲突，原请求不变。                    |
| A03 | 持久提交后、回复前断网或杀进程。            | 同键恢复原结果，不生成第二个订单。              |
| A04 | `DISPATCH_STARTED` 前后分别杀进程。 | 前者可证明未发；后者进入查询对账，不盲重发。         |
| A05 | 撤单与部分成交、全部成交乱序到达。           | 累计成交不重复，真实终态正确，预占只释放一次。        |
| A06 | 业务截止到期后通道恢复。                | 未发送订单不再发出；已发送订单不能被本地过期逻辑伪装成撤销。 |
| A07 | 恢复旧备份后收到旧代变更请求。             | 拒绝旧代请求并要求重新同步，不重复发单。           |
| A08 | 原生 RiskEngine 拒单或初始化失败。     | 有明确持久结果和额度结转，不留下无人处理的已受理请求。    |
